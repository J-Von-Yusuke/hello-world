チャンク化されたオブジェクトの「元サイズ」と「個数」を Navy BlockCache に伝える

Workload Generator / Trace Replay が生成したオブジェクトは、一定サイズを超えるとチャンクに分割されて 保存される。このとき SSD 側の Navy BlockCache から見ると、1 個の巨大オブジェクトは N 個の無関係なアイテムにしか見えない。サイズ別リージョン分割を実装するには、この見え方を 変えて次の 2 つを保証する必要がある。このページはその設計と、そこに至るまでに棄却した案の 根拠をまとめる。

絶対に守る 2 条件
条件これが無いと何が壊れるか
①あるキーを持つアイテムの元のサイズが分かる サイズ別リージョン分割そのものが成立しない。1 MiB チャンクは全部「1 MiB のオブジェクト」に見える
②チャンク化されたコンテンツを重複なく数える(N チャンクなら代表 1 つを 1 と数える) 個数ヒストグラムが N 倍に膨張し、サイズ帯が chunkSize に潰れて分割閾値が読めなくなる

① 何が問題なのか

CacheLib のアイテムは Slab::kSize = 4 MiB を超えられない。ハイブリッド構成でも 必ず DRAM を経由するため、これが全体の天井になる。そこで 1 レコードを固定長チャンクに展開して この不変条件を回避しているが、その代償としてオブジェクトという単位が Navy に届かなくなる。

誤解しやすい点: 4 MiB の上限は「1 アイテムのペイロードのバイト数」にかかるもので、 サイズという数値には無関係。1 GiB でも 4 GiB でも、それを表す整数は 4〜8 バイトである。 天井にぶつかるのは value.size() から論理サイズを推定しようとした場合だけ。 明示的に運べば上限は無い。

② 検討した 3 案と、棄却の根拠

情報を Navy に届ける経路は原理的に 3 つしかない。キー・外部の写像・値である (insertAsync(HashedKey, BufferView) 以外の入口が無いため)。順に検討した。

案 A: キーにサイズを埋める 棄却

<objId 20>_<chunkIdx 6>_<objSize 10> の 38 字固定キーにする案。 サイズは可変属性なので識別子に混ぜてはならないという一点で破綻する。 同一 objId でサイズが変わったとき、(1) 全チャンクが別キーになり偽ミス、 (2) 旧チャンク集合が無効化されず残留して SSD 占有とリージョン占有率が二重計上される。 後者は測定対象である WAF とリージョン指標そのものを汚染する。

原理的にも、チャンク k の中身はバイト範囲 [kC, (k+1)C) であり サイズ変化後も不変なので、重なるチャンクは本来ヒットすべきである。 チャンクの同一性は (objId, chunkIdx) だけで決まる。

これを避けるには「objId → サイズ」を関数にする前処理(初出サイズへの正規化)が要る。 その改変量を全トレースで実測した結果が次表で、tencentBlock ではリクエストの 10.3% が サイズクラスの所属ごと変わる。入力の 1 割の所属を前処理で動かすのでは評価が成立しない。

案 B: 外部のヒント表 棄却

キーは 27 字のまま据え置き、objId → 元サイズ の有界な直接マップ表を別に持ち、 BlockCache がキー先頭 20 桁から objId を parse して引く案。トレース改変は不要になる。

棄却理由は 2 つ。メモリを別途消費すること、そして それは item の lookup table と機能が重複していること。 既にキーからアイテムを引く機構がある系に、キーから属性を引く機構をもう一つ足すのは 構造として冗長である。加えて表は有限なので情報が失われうる (欠落率 ≈ 1 − exp(−M/S)、M ≈ DRAM 容量 ÷ chunkSize)。

この案の副産物のうち chunkIdx 下界は最終設計でも使える。 チャンク k が存在することは、親が少なくとも (k+1)×chunkSize あることを証明する。 ヘッダが読めなかった場合のフォールバックとして有効。

案 C: 値の先頭に埋める 採用

情報をアイテム自身に同居させる。外部状態がゼロになり、値はリージョン内に保存されるので リクレイム時の退避処理でも再起動後でも同じヘッダを読み直せる。

③ 最終設計: 8 バイトの値ヘッダ

各チャンクの値の先頭に 8 バイト置く。obj_size は uint32 なので 4 B で足りる。

代表判定を「キーの規約」ではなく「フラグ」に置く理由

当初は「代表 = chunkIdx が 0」とキーを parse して判定する設計だった。これをフラグに移すと、 BlockCache がキー形式に一切依存しなくなる。oracleGeneral 再生の <objId 20>_<chunkIdx 6> でも、PieceWise の |#| 区切りキーでも、 同じコードがそのまま動く。どのピースを代表にするかは各 generator が決めればよい (oracleGeneral なら chunk 0、PieceWise なら必ず存在する header ピース)。

④ enableLookaside = false への対応

PieceWise-Replay を enableLookaside = false で回すと、挿入は kGet のミス経由ではなく 明示的な kSet で起きる。ヘッダの書き込みを挿入経路ではなく「値を実体化する 1 箇所」に 置くことで、この違いを設計から消せる。どちらの経路も allocate() → 値を書く → insertOrReplace() という同じ流れを通るからである。

BlockCache が行う 2 つの動作(これだけ)
動作対象内容

⑤ 実装: 変更は 4 箇所

1. cachebench/util/Request.h — フィールド 2 つ追加

struct Request {
  // ... 既存 ...
  uint32_t origSize{0};    // 親オブジェクトの論理サイズ (0 = ヘッダを書かない)
  bool     isRep{false};   // このピースを代表として 1 と数える
};

2. Navy 側のヘッダ定義 — 「読むだけ」の構造体

namespace facebook::cachelib::navy {

struct ValueHeader {                  // 8 B, little endian
  uint32_t magicAndFlags;             // 上位 24 bit = magic, 下位 8 bit = flags
  uint32_t origSize;

  static constexpr uint32_t kMagic = 0xCAC5E7;   // 24 bit
  static constexpr uint32_t kRep   = 0x01;       // flags bit0

  bool valid() const { return (magicAndFlags >> 8) == kMagic; }
  bool isRep() const { return (magicAndFlags & kRep) != 0; }
};
static_assert(sizeof(ValueHeader) == 8, "value header must be 8B");

} // namespace

3. CacheStressor — 値を実体化する 1 箇所

auto handle = cache_->allocate(pid, *req.key, sz);
if (handle) {
  if (req.origSize != 0) {
    auto* h = reinterpret_cast<navy::ValueHeader*>(handle->getMemory());
    h->magicAndFlags = (navy::ValueHeader::kMagic << 8)
                     | (req.isRep ? navy::ValueHeader::kRep : 0u);
    h->origSize = req.origSize;
  }
  cache_->insertOrReplace(handle);
}

lookaside の insert-on-miss と kSet がこの経路を共有していることを、実装で必ず確認すること。 共有していなければ、両方から呼ぶ小さなヘルパに切り出す。

6. chained items への対応 — 固定オフセットではなく probe 関数にする

allocateChainedItem() を明示的に呼ばない限り鎖は発生しないので、 sizes[0] しか設定しない現在の generator では chained items は生じない。 ただし鎖が生じても Navy のエントリは 1 個のままである — NvmCache が parent と鎖全体を 1 つの NvmItem に直列化するため、 条件 ② の計数は影響を受けない。変わるのは numBlobs が 1 + 鎖長になることで実データ先頭のオフセットがずれる点だけ。

そこでオフセットを固定値で渡すのをやめ、ヘッダを取り出す関数そのものを渡す。 getBlob(0) が内部で numBlobs を勘定するので、 鎖があってもなくても同じコードが正しい位置を返す。 鎖を使う予定が無くても、こちらの方が堅牢である。 

// navy 側 — 関数の型と 8 B 構造体しか知らない
using HeaderProbe = folly::Function<const ValueHeader*(BufferView) const>;
// BlockCacheConfig::setHeaderProbe(HeaderProbe);

// cachebench 側 — レイアウトを知っているのでここだけで実装する
cfg.setHeaderProbe([](navy::BufferView v) -> const navy::ValueHeader* {
  const auto* ni = reinterpret_cast<const NvmItem*>(v.data());
  if (ni->getNumBlobs() == 0) { return nullptr; }
  auto blob = ni->getBlob(0);                       // parent は blob 0
  if (blob.data.size() < sizeof(navy::ValueHeader)) { return nullptr; }
  return reinterpret_cast<const navy::ValueHeader*>(blob.data.data());
});

書き込み側は parent の割当の先頭に置く。parent は常に存在し、常に blob 0 である。 origSize には鎖の断片長ではなく論理オブジェクト全体のサイズを入れる。

blob 0 が parent であることは単体テストで往復確認すること。 CacheLib の鎖は新しい要素を先頭に繋ぐ連結リストなので、直列化時の並び順が 挿入順と逆になる可能性がある。違っていた場合も probe 関数側だけ直せば済む構造にしておく。

なお鎖でチャンク化を置き換えることはできない。chained items は DRAM で 4 MiB を 超えるための機構だが、Navy 側は kMaxItemSize = 512 × UINT16_MAX ≈ 33.5 MiB が 理論上限である(§1.1 参照)。1 GiB のオブジェクトは鎖でも入らない。 両方を混ぜると不変条件が増えるだけなので、chunkSize を 4 MiB 未満に保って 鎖が発生しない状態を維持するのが最も単純である。現行の 64 KiB / 1 MiB はこれを満たす。

前提として assert すること

  • numBlobs == 1 であること(= 鎖が発生していない)。 §5-6 の probe 関数を使えば鎖があっても動くが、初期段階では 1 であることを カウンタで確認する。0 でない値が出たら generator が意図せず多要素 sizes を 出しているか、config で鎖が有効になっている
  • 値の長さが最低 8 B あること。サイズ 0 → 1 B にクランプされるオブジェクトは 8 + 1 B になる
  • chunkSize = アロケーションクラスサイズ − 35(ヘッダ 8 + キー 27) − アイテムヘッダ長 に合わせ、割当クラス境界を跨がないこと

⑦ 残る既知の系統誤差

オブジェクトのサイズが縮小した後に再投入されると、旧バージョンの末尾チャンクが 孤児として旧クラスのリージョンに残る。二度と参照されないので LRU で抜けるが、 その間はリージョン占有に乗る。これはキー設計や値ヘッダとは無関係な、 チャンク化そのものに固有の現象である。消そうとするのではなく、 孤児チャンク数とバイト量をカウンタに出して報告する。

また「rep の item が在中 = オブジェクトが在中」という計数なので、部分残留 (rep だけ退避されて他チャンクが残る、またはその逆)の間は数え方に近似が入る。 既存の objFullHit% / objPartialHit% と head/tail ヒット率差が そのまま測定器になるので、バイアスの量は数字で示せる。
