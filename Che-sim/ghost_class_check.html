「すぐ戻ってきたコンテンツ」を別の箱に入れると、便乗が消えるか：モデルとシミュレーションでの確認

2026-11-16。例題は 学部生向けの資料 と同じ 4 グループ（S熱・S冷・L熱・L冷、容量 128 MiB、箱 512 KiB × 256 個）。言葉の意味もそちらに合わせた。

結論
  • 名簿を使って分けるだけ（サイズでは分けない）で、OHR 57.7% → 77.0%、BHR 67.6% → 80.0%（シミュレーション、名簿の長さ 5,000 リクエスト）。サイズで分ける今の方法（73.3% / 62.1%）より、BHR が 18pt 高い。
  • 名簿とサイズの両方で分けると OHR 80.9% / BHR 78.9%。人気を前もって知っている理想の 4 分類（81.2% / 81.3%）にほぼ届く。
  • 箱を書く回数（追い出した箱の数）が、混ぜるときの 38 万回から 23 万回に減る（−38%）。書き直しを増やさずに分けられる。
  • 名簿に要るのは、最近消したコンテンツの ID 約 1,000 個（全コンテンツ 88,000 個の約 1%）。
  • Zipf の負荷でも効く（第 5 節）：名簿で分けると、α = 0.5〜1.6 のどこでも、混ぜるより OHR・BHR とも高い。BMR は混ぜるときの 7〜15% 減（α = 0.7〜1.4、容量 10%）、箱を書く回数は 7〜15% 減。サイズで分けると BMR が混ぜるより悪くなるのとは逆。ただし利得は例題より小さい。
  • 実トレースではまだ試していない。

1. 仕組み

  • 名簿：最近消したコンテンツの ID と消した時刻だけを持つ。消してから G リクエスト以内にまた呼ばれたら「すぐ戻ってきた」とみなす。
  • どちらの箱に入れても、書くのはミスしたときの 1 回だけ。書き直し（再挿入）は使っていない。
  • どの箱を消すかは、今までどおり Region LRU（箱の種類をまたいで、いちばん長く呼ばれていない箱）。

2. なぜ効くか（モデルの筋）

消されてから G 以内にまた呼ばれる見込みは 1 − e−(人気 × G)。G = 5,000 なら：

S熱S冷L熱L冷
すぐ戻ってくる見込み31%1%71%3%

人気のコンテンツは名簿に引っかかり、不人気なコンテンツはほとんど引っかからない。だから実績ありの箱には人気のコンテンツが集まって長生きし、不人気なコンテンツは新入りの箱に集まってすぐ消える。不人気なコンテンツが長生きの箱に便乗できなくなる。

容量の内訳（シミュレーション）S熱S冷L熱L冷不人気の合計
サイズで分ける（今の方法）23%31%28%18%48%
名簿で分ける（G = 5,000）23%5%39%30%34%
名簿とサイズで分ける24%21%38%17%37%
理想の 4 分類（人気を知っている）25%13%39%24%36%

BHR を稼ぐのは L熱（バイトで数えたリクエストの 67%）。名簿で分けると、L熱 の容量が 28% → 39% に増え、理想の 4 分類と同じになる。S冷 の便乗が消えた分が、L熱 に回った。

4. 気をつける所

  • 名簿とサイズで両方分けたとき、モデルが外れた（G ≥ 5,000）。モデルは「S熱 の大半が実績あり・小の箱に住む」解に落ちる（容量 62%）。シミュレーションでは S熱 の 86% が新入り・小の箱にいた。立ち上がりで固定された箱が原因かを調べたが、最初の 10% の時期に封じて最後まで残った箱は 0 個で、この仮説は外れた。モデルの答えが 2 つ以上ある（付録 §N.4 と同じ型の）可能性があり、原因は未解決。名簿だけで分ける場合は、すべての G で 1.3pt 以内に合う。
    11-18 追記：§N.4 の「答えが 2 つ」は、実は反復が振動して収束していなかっただけだった（model_fix_1117.html §1）。ghost_model.py も同じ減衰 0.5 の固定で、名簿とサイズの全部の G と名簿だけの G = 2,000 で、300 回の上限まで収束していなかった（残差 3〜4）。減衰の自動調整を入れると全部 70 回以内に収束する。名簿だけは全部の G で 0.2pt 以内に合うようになった。名簿とサイズは OHR 1〜2pt・BHR 5〜7pt 低いまま（旧の 6〜15pt よりは小さい）。収束した解でも S冷 の容量をモデル 31%・実測 21% と多く見積もっており、「答えが 2 つ」ではない別の原因が残る（未解決）。
  • 例題は名簿に有利：人気が「熱か冷か」の 2 段にはっきり分かれている。Zipf では利得が小さくなった（第 5 節）。
  • 名簿は理想化：シミュレーションの名簿は時刻で G 以内かを判定した。実装では、決まった数の ID を入れる表（古いものから捨てる）になる。
  • 人気が時間で変わる負荷、実トレースでは未確認。CDN トレースでは、短い間に束になって来るリクエストが名簿に引っかかりやすく、効き方が変わるはず。
  • 考え方は S3-FIFO や 2Q の「名簿（ghost）」と同じ系統。新しいのは、箱単位で消す SSD キャッシュでの効き方（便乗が消えること）をモデルで説明できる点。

5. Zipf の負荷での確認

負荷は付録 §N と同じ W1 の形：小さいコンテンツ 36 KiB × 20 万個（リクエストの 75%）、大きいコンテンツ 1 MiB × 2 万個（25%）。両方とも人気は順位の α 乗に反比例。容量は全コンテンツの 5% / 10%、箱は容量の 256 分の 1（小さいコンテンツなら 300 個入る）。3,000 万リクエスト、名簿の長さは全部 G = 10,000 にそろえた（後で長さを振った結果も示す）。

容量 5% でも同じ並び（例：α = 1.0 の BMR は 混ぜる 39.4、サイズ 41.2、名簿 35.3、名簿とサイズ 37.7）。全結果は tools/synth/results/ghost_zipf.txt。

  • 名簿で分けると、どの α でも BMR が混ぜるより下がり、OHR も上がる。サイズで分けると、どの α でも BMR が混ぜるより悪い（CDN トレースで見た傾向と同じ向き）。
  • 名簿とサイズを両方使うと OHR は一番高いが、BMR はほぼ混ぜると同じ（α ≤ 0.7 では悪い）。BMR を重く見るなら、名簿だけで分ける方がよい。
  • 利得は α = 1.0〜1.2 が最大で、両端で小さい。

例題より利得が小さい理由：名簿が分けられるのは「消されてすぐ戻ってくるか」だけ。例題では熱と冷の人気が 36 倍違い、すぐ戻ってくる見込みが 31% 対 1% とはっきり分かれた。Zipf では人気がなだらかにつながっているので、境目のあたりのコンテンツはどちらの箱にも入る。

  • α が小さい（0.5）と、人気の差そのものが小さく、すぐ戻ってくるかどうかでほとんど区別できない。
  • α が大きい（1.4 以上）と、人気のコンテンツはほとんど消されないので名簿に載る機会がなく、取り返せるミスもそもそも少ない（付録 §N の (a)）。

6. RegionFlash に実装して、実トレースで確認

hint=ghost（libCacheSim/.../flash/hint/ghost.c）。名簿は ID の数が決まった表で、長さは「SSD にいるコンテンツの数 × frac」（実行中に数える）。追い出した ID を順に入れ、古いものから捨てる。tau= を付けると大きさでも分ける。

合成トレースで ghost_sim と照合：例題 OHR/BHR 76.8 / 79.9（ghost_sim 77.0 / 80.0）、Zipf α = 1.0 で 70.3 / 73.5（同 70.1 / 73.2）、α = 0.7 で 28.5 / 37.3（同 28.7 / 37.6）。分けない・サイズで分けるも RegionFlash の既存の値と一致した。

  • 一番良い frac がトレースで違う（Meta 1、Tencent 0.1、w01 0.3〜1）。決め方は未定。差は Meta 0.11pt、Tencent 0.31pt、w01 0.15pt。
  • 名簿の大きさ：w01 で frac = 1 だと名簿は平均 4,100 万件（ハッシュと輪で約 1.6 GB）。frac = 0.3 で 1,200 万件。実機ならハッシュの代わりに小さな確率的な表（Bloom フィルタなど）で足りるかは未確認。
  • 名簿 + τ の τ は後から選んだ値。実行中に τ を決める方法（SplitThreshold・mini）と名簿の組み合わせは未実装。
  • 再挿入・容量の下限との組み合わせ、FDP のデバイス側の書き込み増幅は未確認。

次にやること
