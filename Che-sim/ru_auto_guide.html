ru_auto の自動設定
3 つの自動の中身、paper に足した 5 構成、ST か BMR 重視かを自動で選ぶ案

スライド形式で 1 つの数値例を通して追う版：ru_auto_walkthrough.html（11-19）。

2026-11-18。コードはlibCacheSim/cache/eviction/flash/（hint/split_threshold.c・util/sst.h・evict/region_basic.c・ssd/rf_ssd.c・ssd/rf_region.c）。理論の番号は appendix_highschool.html（付録の高校数学版）の章。

一言　ru_auto は「何で分けるか（サイズの閾値 τ）」「どれだけ配るか（大の分類の容量の下限 ff）」「何を書き直すか（再挿入の閾値 n）」の 3 つを、走りながら自分で決める。決め方はそれぞれ別で、τ はサイズの分布の形、ff は実測した目的 J の山登り、n は書き直した物が次にまた当たったかの成績、を見る。

1. 全体図：どこで何が自動で決まるか

2. 自動 1：サイズの閾値 τ（SplitThreshold）

規則（util/sst.h の sst_recompute、研究者の規則をそのまま）：書いた物のサイズを 2 のべき乗の桶（1 B〜128 TiB の 48 個）に入れ、「個数」と「バイト」の 2 つのヒストグラムを持つ。10 万受け入れごとに

  1. 個数の中央値の桶 cb と、バイトの中央値の桶 bb を求める（例：小さい物が数では多く、バイトは大きい物が多い）。
  2. bb − cb が 2 オクターブ未満なら分けない（分けるほど離れた裾がない）。
  3. τ = \(2^{\text{mid}}\)、mid = ⌊(cb + bb + 1)/2⌋（2 つの中央値の対数の真ん中 = 幾何平均）。
  4. τ より上のバイトが全体の 5% 未満なら分けない。
  5. 候補はすぐ採用する（hyst_hold=1）。最後にヒストグラムを 15/16 倍して古い分を減らす。
例個数の中央値が 32 KiB（桶 15）、バイトの中央値が 1 MiB（桶 20）なら mid = ⌊36/2⌋ = 18、τ = 256 KiB。256 KiB より大きい物が分類 1（大）になる。
この規則が見ていないものヒット（どちらに分けると当たるか）は見ない。サイズの分布の形だけで決まる「数の多い小さい物と、バイトの多い大きい物を分ける」規則。だから最良の τ からずれることがある：Meta では τ = 1 MiB を選んだ（固定の最良は 32 KiB、BMR は分けない方が良かった）。w01 では 2K〜64K と「分けない」の間を 40 回以上行き来した（固定の最良は 256 KiB）。縮小シミュレーションで τ を選ぶ hint=mini が tune にある。
τ が変わると分類の意味が変わり、自動 2 の「分類 1」の中身も変わる。使われなくなった分類の書き込み中の Region は封じる（seal-on-repartition=inactive）。

3. 自動 2：大の分類の容量の下限 ff（山登り）

下限とは：Region LRU が捨てようとした一番古い箱が分類 1（大）で、しかも大の箱の数が ff × N 以下なら、代わりに別の分類の一番古い箱を捨てる。つまり「大の箱は ff × N 個までは LRU で押し出させない」。ff が自然な取り分（下限なしの 1 本の LRU で大が自然に持つ割合）より小さければ、下限は効かない。

項目中身（evict/region_basic.c の climb）
測る目的窓の中の \(J=\dfrac{\text{ヒットしたバイト}}{\text{リクエストのバイト}}+w\cdot\dfrac{\text{ヒット数（DRAM＋SSD）}}{\text{リクエスト数}}\)、\(w=0.1\)（11-17 に OHR の項を DRAM＋SSD に直した）
窓4N 回の追い出し。Region 1 個 = R バイトなので、窓 = 4NR = キャッシュ 4 杯分の書き込み（SSD 240 GB なら約 1 TB）。短いと「下げた得（小のヒット）はすぐ見え、損（大の再リクエストのミス）は遅れて見える」ので、下げる側に偏る（N 回では 3:1 で 0.1 まで下がった）
出発点温め終わりの後、大が受け入れた1 窓分のバイトの割合（「大の取り分 ≥ 大のリクエストのバイトの割合」の経験則）。累積で数えると、τ が決まる前は全部が分類 0 なので低すぎる値から始まってしまう
刻みと範囲0.02、[0, 0.99]。温め終わりで数え直し、出発点から始め直す
出力P.json の region_policy：ff_end（最後の値）、ff_mean（追い出しの選択ごとの平均）、picks
理論コンテンツ単位の静的分割なら J は配分の凹関数（高校版 第 4・19 章）→ 山は 1 つ → 山登りは最良の格子点の ±0.02 を行き来し、本当の最適の 2 刻み以内に収まる。Region LRU の J が単峰であることは合成負荷の格子でしか確かめていない
実トレースで効いてくる制約窓 1 つでキャッシュ 4 杯分を書くので、1 本の実行の窓の数 = SSD に書いた量 ÷ (4 × キャッシュ容量)。たとえば全体で 30 TB 書くトレース（SSD 240 GB）なら窓は約 30 個で、ff は出発点から最大 30 × 0.02 = 0.6 しか動けない。出発点が遠いと最良に着く前にトレースが終わる。後で出す提案（§5）は、この「出発点の悪さ」を避けるためのもの。

4. 自動 3：再挿入の閾値 n（分類ごと）

  1. 決め方：分類 c、ヒット数 h（1〜8）ごとに「その h で書き直した物が、次の滞在で 1 回以上当たった」の試行数 try と当たり数 hit を数える。ラプラスの継起則 \((\text{hit}+1)/(\text{try}+2)\) が target（0.5）以上になる最小の h を、その分類の n にする（どの h も届かなければ n = 9 = 書き直さない）。
  2. 使い方：箱を捨てるとき、中の物の h（その滞在の SSD ヒット数）が n 以上なら書き直す。0 < h < n の物も確率 0.02 で書き直す（学び続けるための探索）。h = 0 は書き直さない。追い出す箱 1 つあたり R × 0.5 バイトまで（max_frac）。
  3. 学び方：書き直した物は「書き直した時の h（8 で頭打ち）」と（11-18 から）「書き直しを決めた分類」を覚えておき、次に追い出される時に、その滞在で当たったかを 1 件数える。出力は P.reauto.json（分類ごとの try・hit・各 n が使われた回数）。
  4. 理論：当たった回数の多い物ほど次も当たりやすい（ベイズ。高校版 第 20 章）ので「h ≥ n なら書き直す」という閾値の形が最適。target = 0.5 は「防げるミス 1 回あたりの追加の書き込みが物 1 個分まで」という方針の値で、導出した値ではない。
11-18 に直した不具合（mode=ii と組み合わせたとき）以前は成績を「物がいま居る分類」に数えていた。mode=ii では書き直した物が専用の分類に移るので、成績は専用の分類にだけ数えられ、元の分類（小・大）は何も学ばずに n = 1（何も知らないときの既定：(0+1)/(0+2) = 0.5 ≥ 0.5）のままだった。書き直しを決めた分類に数えるように直した（ssd/rf_region.c、物の情報に 1 バイト re_c。物の情報の大きさは 32 B のまま）。小さな合成負荷（W1 の形、300 万要求）での確認：

保証されないこと書き直しを増やすと容量を使い、\(T\) が縮み、また当たる確率が下がる。n を決め直し続けるとこの釣り合いに落ち着くが、そこが目的 J の最適である保証はない。下限の山登り（自動 2）とも同じ容量を取り合う。

3 つの自動の絡み方

τ（自動 1）ff（自動 2）n（自動 3）
変えるものどの物がどの分類か分類どうしの容量の取り分どの物を書き直すか
他への影響τ が変わると「分類 1」の中身が変わり、ff の意味も変わる大の寿命が変わり、大の物が「また当たる」確率（n の成績）が変わる書き直しが容量と書き込みを使い、J と ff の山の位置を動かす
見ている量サイズの分布だけ実測の J（全部の効果の合計）書き直した物の次の成績

J を直接測っているのは自動 2 だけなので、τ と n のずれは、ff がそれを含めた上で一番良い所を探す、という分担になっている。

(a) mode=ii と CacheLib の priority、PID

  • CacheLib：書き直した物の priority は min(前回の書き込みからのヒット数, numPriorities − 1)、新しく入れる物は一番低い priority（navy/block_cache/BlockCache.cpp の reinsertOrRemoveItem と allocateForInsert）。Allocator は priority ごとに別の RegionAllocator を持ち、別の Region に書く（Allocator.cpp の allocate、allocateWith の region.setPriority）。priority が 2 段なら「新しい物の Region」と「書き直した物の Region」に分かれる。
  • RegionFlash の mode=ii：書き直した物を、元の分類ではなく 1 つの専用の分類（分類番号 = 分類の数）に入れる。分類 = 書き込み口 = 開いている Region なので、CacheLib の priority 2 段と同じ分かれ方になる（書き直しには h ≥ n ≥ 1 が要るので、priority が 1 になる物だけが専用に入る点も同じ）。
  • PID：R = RU では、別の Region = 別の RU なので、書き直した物は新しい物と同じ RU に混ざらない。FDP の PID（RUH）を分けるのと同じ。R = 256 MiB で FDP の模型（ru-size）を使うなら、分類 c は RUH c mod ruh に行く。
  • 違い：CacheLib で priority を使うのは Segmented FIFO（priority の高い Region ほど後で捨てる）。ru_auto_ii の追い出しは Region LRU のままで、書き直した物の Region は touch が多ければ自然に長生きする。Segmented FIFO で比べるなら region-evict=sfifo,region-params=ratio=1:1（ii の分類は一番上の段に入る）。

(b) DRAM でのヒット数で 2 分割（動的か固定か）

  • CacheLib と同じ動き（inclusion=cachelib）では、SSD に書くのは DRAM から出た物で、その時「DRAM にいた間に何回当たったか」が分かる（物の情報の dram_hits）。サイズと違い、人気そのものの手がかり。高校版 第 24 章の「DRAM は SSD と切り離せる」から、この回数は SSD 側の方式によらない。
  • 動的（k=2）：DRAM ヒット数 + 1 の log2 の桶ごとに書いたバイトを数え（10 万受け入れごと、古い分は 15/16）、バイトが半々になる桶で切る。どちらの分類にも空でない桶を 1 つ以上残す。0 回の物がバイトの半分以上を占める負荷では、結果として「0 回 / 1 回以上」と同じになる。
  • 固定（thr=1）：DRAM ヒット数 + 1 が 1 以下（0 回）と 2 以上（1 回以上）。
  • 「動的に二分割できないか」への答え：動的にはすでになっているが、境界の決め方は「バイトが半々」で、目的（BMR・J）を見ていない。目的で決めるなら、hint=mini がサイズの τ でやっているのと同じく、候補の境界（0 / 1 / 3 / 7 回）ごとに縮小した影のキャッシュを回して J の良いものを選ぶ形になる。DRAM のヒット数は SSD の方式によらないので、影のキャッシュは本物の DRAM から出る列をそのまま使える。未実装。

(c) OHR 寄り：下限なし（「配分を決めない」と OHR 寄りになる理由）

下限なしの 1 本の Region LRU では、各分類の取り分は「1 バイトあたりの touch の率 ≈ \(\lambda/s\)」で決まる（高校版 第 12 章）。これは OHR の上限の詰め方（\(\lambda/s\) の順、第 4 章）に近く、BMR の詰め方（\(\lambda\) の順）とは逆向き。W1・容量 10% のモデル：小の取り分は自然な配分 61.5%、OHR 最適 80%、BMR 最適 5%。実測 OHR は自然な配分 64.0（混在 51.8）、BHR は 51.8（混在 56.6）。だから「配分を決めない」＝ OHR 寄り、という理解で合っている。再挿入の有無は、書き直しが OHR を上げつつ書き込みを増やすので、両方を並べた。

6. 提案：ST だけか BMR 重視かを自動で選ぶ

一言　選ぶべきは「大の分類に下限（容量）を足すと、目的 J が上がるか」。それは自然な配分の点での限界値の比べ合い（KKT の判定）で決まる。大の物が追い出された直後にほとんど再リクエストされないなら（w01 のような負荷）、足しても得はなく ST だけで最適。そうでなければ、指定の w で下限の山登りに移る。ユーザが決めるのは w だけになる。

6.1 理論：いつ ST だけで十分か

下限なしの自然な配分で、大の分類に容量を少し足したときの J の増え方 \(\nu_L\) と、小から少し減らしたときの J の減り方 \(\nu_S\) を比べる（高校版 第 19 章の限界値。大きさが 1 種類の分類では）：

\[ \nu_k=\Big(\frac{1}{\Lambda_B}+\frac{w}{s_k}\Big)\,\lambda^{\rm edge}_k,\qquad \text{ST だけで十分}\iff\nu_L\le\nu_S\ \ (\text{自然な配分の点で}). \]

\(\lambda^{\rm edge}_k\) は分類 k の「捨てられる寸前（端）のコンテンツ」の人気。ご質問の「λ/s か λ か」は w が決める：

  • \(w=0\)（BMR だけ）：比べるのは \(\lambda^{\rm edge}\)（大きさで割らない）。
  • \(w\to\infty\)（OHR だけ）：比べるのは \(\lambda^{\rm edge}/s\)。
  • 使うのは分類の平均の人気ではなく端の人気。大の分類に「いつも棚にいる少数の超人気」と「二度と来ない大多数」がいる場合、平均の λ は高いが、容量を足して救えるのは端（二度と来ない側）なので価値は 0。

自然な配分は \(\lambda/s\) をそろえる（OHR 寄り）ので、大の物が再リクエストされる負荷では、BMR の目で見ると大の端の価値が小より高い（W1 で大のヒット 1 回は小の 28 倍の価値）→ 下限が効く（W1 のモデルで BHR +5pt）。大の物がほとんど再リクエストされない負荷では \(\lambda^{\rm edge}_L\approx0\) なので \(\nu_L\approx0\) → ST だけで最適。ご提案の「大サイズに本当にリクエストがないなら ST で十分」は、この判定の特別な場合にあたる。

判定は「自然な取り分の点での坂の向き」だけ見ればよい。坂は ff を少しだけ上げて J を測れば分かる。

6.2 アルゴリズム（試しの下限で坂を測る）— 11-18 に実装：region-params=auto=1/w=0.1/gate=1

状態 ST（ff = 0：下限なし）で始める。分類（τ）と n=auto はどちらの状態でも今と同じに動かす。
窓（4N 回の追い出し）ごとに J を測る。
ST のとき:
  a ← 大の箱の数 ÷ N（自然な取り分。窓の平均）
  b ← 大が受け入れたバイトの割合（山登りの出発点）
  K 窓ごとに 1 窓だけ「試し」: ff = a + max(0.05, 0.5 × (b − a))       … 出発点までの中間。0.05 だけでは差がゆれに埋もれた
  ΔJ = J(試し) − ( J(試しの前の ST 窓) + J(試しの後の ST 窓) ) / 2      … 前後の平均で負荷の変化を打ち消す
  ε = 2 × ΔJ のゆれの標準偏差 = 2 × √(E[s²]) / 2                        … s = 続いた 3 つの ST 窓の J の 2 階差分
                                                                          （1 階差分では温め直後の J の上昇まで「ゆれ」に数えた）
  ΔJ > ε が 2 回続いたら → 山登りへ（出発点 = max(a + Δ, 大が受け入れたバイトの割合)、向き = 上）
  そうでなければ ST のまま（試しの間隔を K ← 2K に延ばす。上限あり）
山登りのとき:
  今の perturb and observe（刻み 0.02）
  ff ≤ a（下限が効いていない）が M 窓続いたら → ST に戻る
  • コスト：ST のときの追加の損は試しの 1 窓だけ。山登りの出発点の悪さ（§3 の「窓の数が足りない」）は、w01 型では起きない（山登りに入らない）。W1 型では今と同じ出発点（受け入れバイトの割合）から始める。
  • w の効き方：OHR を重く見る（w が大きい）ほど小のヒットの価値が上がり、試しで J が上がりにくいので、ST のままになりやすい。BMR 重視（w = 0）では、大が再リクエストされる限り山登りに入る。
  • 実装：evict/region_basic.c の gate_step（状態 4 つ：s 下限なし・p 試し・a 試しの次の窓・c 山登り）。引数 gd（0.05）・gm（0.5）・gz（2）・gneed（2）・gk（2）・gkmax（32）・gback（8）。新しい記憶は要らない。経過は P.json の region_policy.gate（試しの ΔJ と ε、窓ごとの状態の列）。gate を付けない構成はビット単位で前と同じ（確認済み）。
別案：名簿で限界値を直接測る（試しをしない）追い出した物の名簿（ID・大きさ・追い出した時刻・分類）を分類ごとに持ち、ミスした物が名簿にあれば「追い出してから何リクエスト後か」を数える。分類 k に容量を δC 足すと、その分類の物は \(G_k=\delta C/(\text{分類 } k \text{ の追い出しバイトの率})\) だけ長くいられるので、「追い出してから \(G_k\) 以内に来たリクエスト」の J の価値の合計が、δC を足したときの J の増え方の見積りになる。大と小で比べれば KKT の判定がそのまま測れる。ただし Region LRU では、そのリクエストが箱を touch して延命させ、さらにヒットを生む（高校版 第 21 章）。この連鎖は 1 箱の数の多い小で大きく、名簿の見積りは小の価値を低く見て下限を選びやすい。山登りに入った後は実測の J で直るので致命的ではないが、試しの案より実装（名簿の記憶と、ミスでの照合）が重い。

つまり、ご提案の「ST か BMR 重視かを選ぶ」は、ru_auto の山登りがすでに暗に行っている。gate が役に立つのは「下限が強く害になり、しかも窓が少なくて山登りが下がり切れない」負荷に限られる。そういう実トレースがあるかは未確認なので、gate はオプション（PAPER_GATE=1 で paper に足す）として残した。
