BigHash ログ構造化 (第 3 版)

仕組み: 論理バケット→物理スロットの対応表を持ちます(バケットあたり 14B、1.5GiB の BigHash で約 5.5MB)。バケットの書込は subRegion 大(16MiB = 4096 バケット)のバッチバッファへ追記し、満杯になったら 1 回のデバイス書込で出します。書込ヘッドが次の RU に入ると、最新コピーがその RU にあるバケットだけを空にします(RU 単位の削除)。読出はデバイスを読んだ後に対応表を再確認するので、途中でスロットが再利用されても誤読しません(stale 判定 135 回)。書込は時刻順・連続になるので、FDP の物理 RU 配置と揃います。

実測(小オブジェクト 85%、8M ops、BC は SR モードで同一):

根本原因(容量崩壊): 1 件挿入するたびに 4KiB のバケット全体がヘッドへ移動し、RU 退避は「しばらく書き換えられていないバケット」を丸ごと消します。3 RU 構成だと、生き残るのは直近 2 RU 分の書込(約 26 万回)で触られたバケットだけです。393k バケット中おおよそ 393k×(1−e−0.67) ≈ 19 万が上限で、しかも退避後に入った少数のアイテムしか持ちません。in-place 方式は全バケットを常に満たしたまま、バケット内で古いものから押し出すので、利用率が根本的に違います。

選択肢: (a) RU 退避時に生存バケットを先頭へコピーする GC(論理バケット数を減らして過剰領域を確保。WA = 1/(1−利用率)。FairyWREN 型)、(b) DRAM 上でバケットごとに挿入をまとめて書く(Kangaroo の KLog 型。1 回のバケット書込に多数のアイテムを載せる)、(c) 両方。既定(navyBigHashRuMode: false)は in-place のままで、影響はありません。

Nemo (簡易版) — 第 4 版

切替: "navyBigHashMode": "inplace" | "log" | "nemo"、navyNemoSetGroupSizeMB(既定 64)、navyNemoFlushThreshold(既定 = SG 内セット数の半分)、navyNemoHotFraction(0.3)。実装は navy/bighash/NemoCache.{h,cpp} で、Engine として BigHash と差し替わります。

  • Set-Group(SG): 4KiB のセット(BigHash の Bucket 形式)の集まり。キーはどの SG でも同じ位置 hash % セット数 に入ります(小さいハッシュ空間 → 衝突させて充填率を上げる)。
  • DRAM に SG を 2 つ持ちます(OLD = 次に flush、NEW = OLD のセットが満杯のときの受け皿)。溢れた挿入の数がしきい値に達したら、OLD を 1 回の連続書込で flash に出します。
  • flash 上の SG は FIFO のリングです。書込先スロットにある最古の SG を退避し、古い 30% の区間でヒットした hot オブジェクトは、より新しいコピーが無いことを Bloom filter で確認したうえで、flush 中の SG に再挿入します。
  • 索引は (SG, セット) ごとの Bloom filter で、全部 DRAM に置きます(論文の flash 上の索引プールは省略)。削除は tombstone で行います。

第 6 版: 再挿入・FDP 順序・SFIFO

  • PI 再挿入の victim SR 採用: reclaim 中の SR は先頭から空になっていくので、空いた subRegion を reclaim スレッド自身の再挿入先として使い(PID は増やさない)、reclaim が終わったらその PID の open SR として残します。通常の挿入は reclaim が終わるまで待ちます。PI・clean=1 での再挿入失敗率は 8.1% → 4.4〜6.8%(2 回測定、成功 431k → 451k)。buffer を 12 に増やしても 6.4% で、残りの原因は未特定です。
  • RUH Update の順序保証: SR を開いた時点ではなく、SR の最初の書込の直前に、その PID の直前の SR の全 subRegion が書き終わったことを確認してから updateReclaimUnit(handle) を呼びます(待ちが 200ms を超えたら navy_bc_ruh_order_timeouts に計上。実測 0)。直前の SR の最後の書込が新しい RU に混ざることを防ぎます。
  • SFIFO のセグメント: PID ではなく「初回挿入の SR = 0 / 再挿入(II)の SR = 上位」にしました。PI ではセグメントは 1 つで FIFO と同じです。
  • SR 256MiB(退避候補 約 7 個)でのポリシー比較(II, clean=2, 6M ops): LRU 22.67% / FIFO 22.80% / SFIFO 23.05%。SR 単位の LRU は FIFO と差が出ません(どの SR にも常にヒットがあり、最近性が SR 間でほとんど差を持たない)。

Nemo 非同期 flush — 第 5 版

DRAM の SG を 3 つ(NEW / OLD / FLUSHING)にし、flusher スレッドが「最古スロットを引退 → 読み出して hot を FLUSHING に再挿入 → 連続書込 → 公開」を行います。排他ロックは役割の入れ替えと公開の一瞬だけで、デバイス I/O 中は取りません。FLUSHING を変更するのは flusher だけで、削除は NEW 側の tombstone で隠します。

1. 構造: SuperRegion = 旧 Region、subRegion = バッファ単位

  • 1 つの placement が同時に開ける SR は 1 個。全 subRegion を払い出し終えると次の free SR を開きます(RegionManager::getCleanRegionSR)。
  • 退避は SR 単位の FIFO で行い、元の LRU/FIFO policy は SR モードでは使いません。R=1・placement 1 個の SR モード = Region 単位 FIFO になります。SR モードを off にすれば既存コードには一切入らず、priority も容量配分も元のままです。
  • subRegion サイズは SR の約数かつ 16〜256MiB に自動補正します(指定値に最も近いもの。例: 20MiB → 16MiB)。
  • FDP: placement ごとに allocatePlacementHandle() を取り、書込にはその SR の handle を使います。Device::updateReclaimUnit(handle) と onReclaimUnitFreed(off,len) は既定では何もしない仮想関数なので、ioctl を差し込んでください。

2. 元サイズの伝達経路

カナリア(flags の上位 16bit)で自己検証します。レイアウトがずれると navy_bc_header_miss が増えるので、誤分類が黙って続くことはありません。sizeof(CacheValue) は 24→32B になりますが、getSize()=max(size,32) なので割当サイズは変わりません。

3. 実測で見つけた 3 つの不具合と根本原因

① in-mem buffer 枯渇デッドロック

現象: II(3 ヒント×2 = 6 placement)で 0.04M ops のまま停止し、Failed to assign buffers. All buffers(2) が出続けた。
根本原因: 開いている region は満杯になるまで buffer を 1 つ専有する。placement 数 > buffer 数だと、全 buffer が「半端に開いた region」に握られて誰も flush できない。元の CacheLib でも numPriorities を増やすと起きる潜在問題。
修正: numInMemBuffers ≥ 2 × placements に自動で引き上げる。

② reset 時に全 SR が「sealed」扱いになる

計測ログ: 起動直後、どの SR も open されていないのに sealed sr=0..4 が出ていた。
根本原因: RegionManager::reset() → resetEvictionPolicy() が全 region に track() を呼ぶ(元実装では「空 region を policy に登録する」意味)。SR モードでは track = 「flush 完了」なので、全 SR が free と sealed の両方に入り、開いている SR を回収して状態が壊れた。
修正: SR モードの resetEvictionPolicy は SR 状態の初期化だけを行い、track しない。

③ seal されても reclaim が起動しない

根本原因: reclaim の予約を「領域要求時」にしか行っていなかった。全 writer が free SR 待ちで寝た後に SR が seal されても、起こす人がいない。
修正: markRegionSealedSR 自体が不足分の reclaim を予約する。

修正後(ユーザー提案サイズ, 6M ops): SR open 82 / reclaim 77、header_miss 0、BigHash wipe 8 回 = 831,536 アイテム(BigHash 退避 831,583 とほぼ一致)。ヒット率 23.5%。

6. 未対応・今後の課題(正直に)

  • Placement ID の統合・縮小(PID ごとの書込帯域が RU の Open 時間上限に満たない場合に、ヒントを PID に束ねる機能): 未実装。navy_bc_placement_N_inserts を時間軸で見ると、帯域判定の入力になる。
  • PI の「待つ」: reclaim スレッドの中で free SR を待つと、自分しか作れない SR を待つ自己デッドロックになる。そのため現状は再挿入失敗(navy_bc_reinsertion_errors, 実測 8.8%)として数えている。navyCleanSuperRegions を増やせば減る。
  • DRAM 上のアクセス回数をヒントに使う: NvmItem にその情報が無い。CacheValue の空き領域に載せる設計は可能だが未実装。
  • BigHash の一括書込: BigHash はバケット単位の in-place 更新が本質で、未対応。RU 削除は世代番号を上げる方式なので書込は 0。ただし wipe と同時に走っていた挿入 1 件が失われうる(統計上は無視できる)。
  • SR モードは persist/recover 非対応(再起動時は空から開始)。
  • リクエスト単位のヒント(SplitThreshold の拡張)は API を分けてあり、BlockCache::hintOf の 1 箇所を差し替えればよい。
